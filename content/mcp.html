Connect the MCP server#

The agent skill teaches your assistant to write the integration — but it still needs a project and an ingest key to write in, and those only exist once someone opens the dashboard and makes them. The MCP server closes that gap. Connect it once and your assistant can create the project, read back the key, and hand it straight to the skill.

The result is that "set up Pulse for acme.com" works start to finish, without you leaving the conversation.

It is on by default and needs no configuration beyond the SUPABASE_SERVICE_ROLE_KEY you already set for ingestion. Your instance serves it at:

https://your-pulse.vercel.app/api/mcp

Add that as a custom connector and you're done. There is no API key to generate or paste — the server speaks OAuth 2.1 with PKCE and dynamic client registration, so your assistant discovers the endpoints itself, sends you to a consent screen, and you approve it by name.

ClientHow to add it
Claude (web, desktop)Settings → Connectors → Add custom connector → paste the URL
ChatGPTSettings → Connectors → Create → paste the URL
Claude Codeclaude mcp add --transport http pulse https://your-pulse.vercel.app/api/mcp
Cursor, Zed, othersAny MCP client with remote HTTP + OAuth support

The transport is Streamable HTTP, not SSE. SSE was removed from the MCP spec in 2025 and supporting it would mean running Redis — which would break Pulse's promise that a deployment needs nothing but Vercel and Supabase.

What it can do#

Four tools, scoped to setup and nothing else.

ToolDoes
list_projectsNames, slugs, domains and timezones for everything on the instance.
create_projectCreates a project and returns its ingest key plus a paste-ready snippet.
get_project_keyIngest key and install snippets for one existing project.
update_project_domainsReplaces a project's domain allow-list. Replaces, not merges — send the full list.

Domains are normalized on the way in, so an assistant that passes whatever the user typed still gets it right: https://www.Acme.com/pricing is stored as acme.com.

What it deliberately can't do

There is no tool to delete or archive a project, rotate an ingest key, read visitor or revenue data, or change public-page visibility. Two reasons, and they're worth stating plainly:

  • An assistant acting on a misread instruction should not be able to cause a loss you can't undo.
  • Your analytics are not something a connected app needs to see in order to set up tracking.

Those operations stay in the dashboard, where a human is doing them on purpose.

The ingest key these tools return is public by design — it ships in your page source either way, and the domain allow-list is what actually stops spoofed data. It is safe for an agent to write into a repo or commit.

Pairing it with the agent skill#

The MCP server and the agent skill solve opposite halves of the same job, and they're designed to be used together:

MCP serverAgent skill
Answers"What project and key do I use?""What code do I write, and where?"
Runs againstYour Pulse instanceThe repo you're editing
InstallOnce, per assistantOnce, per project you track

Install the skill in the project you want to track:

npx skills add DevMello/pulse --skill add-pulse-analytics

With the connector added and the skill installed, the whole setup collapses into one sentence:

Set up Pulse analytics for this app. It's deployed at acme.com.

Your assistant creates the project through MCP, gets the key back, then follows the skill to detect your framework, choose the script tag or @pulse/sdk, wire the right adapter, avoid the classic double-pageview mistakes, and verify events actually reach the collector before calling it done.

They work fine apart, too. Without the skill, MCP still gets you a project and a snippet to paste. Without MCP, the skill still does the integration — you just paste the key in yourself, as in Option C of the quick start.

Managing access#

Everything lives under Connected apps at /app/settings.

The master switch

Turning MCP off takes effect immediately — discovery starts returning 404 and every live token stops working on its next request. It's a pause, not a purge: approved apps are kept, so turning it back on restores them without re-authorizing each one.

Per-app disconnect

One click revokes that grant and every token issued under it. The app has to ask again, and you have to approve it again.

Access tokens last an hour. Refresh tokens rotate on every use, and presenting an already-used one is treated as theft rather than a mistake — the entire grant is revoked on the spot.

Leaving this on exposes an open registration endpoint. That's what the MCP spec requires, and it is safe on its own — a registered client holds no access at all until you approve it by name on the consent screen, and unapproved registrations are swept away daily. But it is a real thing to know about your deployment, and if you'd rather not run one, the switch is right there.
