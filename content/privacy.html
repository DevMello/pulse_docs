Opt-out & Do Not Track#

Pulse sets no cookies, writes nothing to localStorage, uses no fingerprinting, and does no cross-site tracking. There are three ways an individual visit can be excluded.

The pulse_ignore flag

Set a single localStorage key in any browser you don't want counted — your own, mainly, or a staging environment. The SDK reads this flag on every send and never writes it.

// Run once in the browser's console, or from your own admin UI
localStorage.pulse_ignore = '1';

// To start counting yourself again
delete localStorage.pulse_ignore;

Do Not Track & Global Privacy Control

Opt in to honouring DNT / GPC with respectDnt: true (or the data-respect-dnt attribute). When on, events from browsers signalling either preference are dropped. The collector also checks the DNT and Sec-GPC request headers, so the preference is respected even if someone posts to the endpoint directly rather than through the tracker.

How unique visitors are counted

No identifier is stored. A visitor is a salted daily-rotating hash computed on the server:

sha256( daily_salt + project_id + ip + user_agent )

Every input except the salt is already in an ordinary HTTP request, and none of them is stored — the IP is used to compute this and look up a country, then discarded. The salt is random per UTC day and destroyed after 48 hours, after which that day's hashes can't be recomputed or reversed by anyone, including the site owner. That's what makes "we can't track you across days" a property of the system rather than a promise.

Excludes, localhost & bots#

Excluding paths

Skip routes with exclude (SDK) or data-exclude (script). Exact match, or prefix match with a trailing *.

init({
  key: 'YOUR_KEY',
  host: 'https://your-pulse.vercel.app',
  exclude: ['/admin*', '/preview', '/checkout/success'],
});

Localhost & development

By default Pulse does not track localhost, 127.*, ::1, *.local, or file:// pages, so your dev server never pollutes real numbers. Opt in with trackLocalhost: true or data-local when you specifically want to test the pipeline end to end.

Bot filtering

The tracker skips obvious automation client-side as a cheap optimization — it checks navigator.webdriver and known headless globals (_phantom, __nightmare, callPhantom) and simply doesn't send the request. The real filtering happens on the server against a maintained bot list, at a per-project sensitivity level. Bot events are dropped quietly (202) rather than stored.

Domain allow-list#

Because the ingest key is public, it can't be what authorizes a write. The real defense against forged events is your project's domain allow-list, configured in the dashboard. If set, the collector only accepts events whose URL hostname matches.

  • An entry also covers its subdomains — adding example.com accepts www.example.com and blog.example.com too.
  • A leading www. is normalized away on both sides.
  • If the list is empty, all domains are accepted (convenient for getting started; tighten it before you publish a stats page).

The allow-list is why it's safe to expose data-key in your HTML: an event forged from another domain is rejected before it's ever stored.
