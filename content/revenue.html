Revenue tracking#

Revenue is a first-class citizen in Pulse. Anything you can't wire to Stripe — Gumroad, Lemon Squeezy, Paddle, a manual invoice, an ad payout — you can report through the SDK, and it lands in the same pipeline as your Stripe webhooks. Every money query then reads one table.

Two equivalent forms

import { track, trackRevenue } from '@pulse/sdk';

// Dedicated helper (clearest)
trackRevenue('purchase', { amount: 29, currency: 'USD' }, { plan: 'pro' });

// Or inline on any event
track('purchase', { revenue: { amount: 29, currency: 'USD' }, plan: 'pro' });
// Script tag — revenue rides inside props
pulse('purchase', { revenue: { amount: 29, currency: 'USD' } });

Amounts are in major units

Pass 29 for $29.00 — not 2900. The collector converts to integer minor units in the currency you charged, so nothing is ever stored as a float. Zero-decimal currencies like JPY and KRW, and three-decimal ones like KWD, are handled correctly server-side.

FieldTypeNotes
amountnumberMajor units. Must be finite and ≥ 0 — a NaN or negative amount is rejected outright rather than coerced to zero, because a corrupted public revenue figure is the one number people actually check.
currencystringISO 4217, case-insensitive. Defaults to USD if omitted or malformed.

Where it shows up

SDK revenue is stored as a normalized record with source: 'sdk' and kind: 'one_time', alongside Stripe rows. It appears on the dashboard's revenue view and — if you've enabled revenue on the public page — in the public totals. If you've set PULSE_FX_RATES on your deployment, mixed currencies are normalized into one display total; anything unconverted is flagged in the UI rather than silently misreported.

A revenue event is also a regular event — the purchase is recorded even if the money side fails. If the revenue row can't be written, the pageview/event is still durable and the failure is logged server-side, never surfaced to the fire-and-forget client.
