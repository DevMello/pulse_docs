Pulse SDK · Documentation

Track pageviews, events & revenue in one line.

The Pulse SDK is how your site talks to your self-hosted analytics. Drop in a ~1 KB script tag, or install the typed @pulse/sdk package with first-class adapters for React, Vue and Svelte. No cookies, no consent banner, nothing stored on the device.

Quick start API reference
928 B gzipped Zero cookies No dependencies TypeScript types React · Vue · Svelte MIT licensed

What the SDK does#

Every Pulse integration boils down to sending three kinds of signal to your collector: pageviews, custom events, and revenue. The SDK is a thin, fire-and-forget transport for those signals — enrichment (device, browser, country, referrer grouping) all happens server-side, so the client stays tiny and leaks nothing.

Pageviews

Tracked automatically on first load and on every SPA route change, deduped against the last URL sent.

Custom events

Any named event with optional scalar properties — signups, clicks, feature usage, funnel steps.

Revenue

Attach an amount and currency to any event. It lands in the same pipeline as your Stripe webhooks.

Script tag vs. npm package#

There are two ways to install Pulse, and the plain script tag does everything the SDK does. The npm package is optional sugar — reach for it only when you want typed helpers and route tracking wired into a framework.

 Script tag@pulse/sdk

Not sure? Start with the script tag. You can always add the npm package later — they hit the same endpoint and produce identical events, so nothing about your data changes if you switch.

Quick start#

Grab your project's public ingest key from the Pulse dashboard (Project → Settings), then pick a path below. Your first pageview should land within seconds.

Option A — the script tag

Paste this before </body>. That is the entire integration.

<script defer data-key="YOUR_INGEST_KEY" src="https://your-pulse.vercel.app/px.js"></script>

Swap your-pulse.vercel.app for your own deployment's origin, and YOUR_INGEST_KEY for the key shown in the dashboard. The key is public by design — it ships in client code, and the domain allow-list (not the key) is what stops forged events.

Option B — the npm package

npm i @pulse/sdk
import { init, track, trackRevenue } from '@pulse/sdk';

init({
  key: 'YOUR_INGEST_KEY',
  host: 'https://your-pulse.vercel.app',
});

// Custom event
track('signup', { plan: 'pro' });

// Revenue
trackRevenue('purchase', { amount: 29, currency: 'USD' }, { plan: 'pro' });

Calling init() starts automatic pageview tracking immediately. Everything else — events, revenue, framework helpers — builds on top of that.

The script tag

Adding the script#

The tracker is a single self-hosted file — px.js, served from your own Pulse deployment. It sets no cookies, writes nothing to storage, and wraps its entire body in try/catch so a failing analytics call can never break the host page.

<script defer data-key="YOUR_INGEST_KEY" src="https://your-pulse.vercel.app/px.js"></script>
defer
Load the script without blocking rendering. Recommended, but not required.
data-key
Required. Your project's public ingest key. Without it the script does nothing and returns silently.
src
Points at /px.js on your deployment. The collector origin defaults to this URL's origin unless you override it with data-host.

All behaviour is configured through data-* attributes on that same tag — there is no separate config object for the script build.

Configuration: data-* attributes#

Attributes are read once, from the script tag itself, when the tracker loads. Boolean flags are toggled by presence — the attribute needs no value.

AttributeTypeDefaultWhat it does
data-key required string — The project's public ingest key. If missing, the tracker returns immediately and sends nothing.
data-host string script origin Override the collector origin. Useful if you serve px.js from a different host than your Pulse app.
data-manual flag off Disable automatic pageview tracking. You drive pageviews yourself by calling pulse().
data-respect-dnt flag off Drop events from browsers sending Do Not Track or Global Privacy Control signals.
data-local flag off Also track localhost, 127.*, ::1, *.local and file://. Off by default so development traffic doesn't pollute your numbers.
data-exclude string — Comma-separated paths to skip. A trailing * makes it a prefix match.

Example: a fully configured tag

<script
  defer
  data-key="YOUR_INGEST_KEY"
  src="https://your-pulse.vercel.app/px.js"
  data-respect-dnt
  data-exclude="/admin*,/preview,/draft*"
></script>

This tracks everything except your admin area and preview/draft routes, and honours Do Not Track. Pageviews are still automatic because data-manual is absent.

Excludes are also enforced server-side. Each project has its own Excluded paths setting in the dashboard that applies to all traffic regardless of the tag. Use data-exclude for per-page-embed control; use the dashboard setting for a project-wide rule.

The pulse() function#

Once the script loads it exposes one global: window.pulse. Its signature is deliberately minimal.

pulse(name: string, props?: object) => void

Track a custom event

pulse('signup', { plan: 'pro' });
pulse('cta_click', { location: 'hero' });
pulse('video_play');            // properties are optional

Track a pageview manually

Call pulse() with no name, or the name 'pageview', to record a pageview for the current URL. This is what you use in data-manual mode.

pulse();            // pageview for the current URL
pulse('pageview');  // identical

Track revenue

Revenue rides along inside the props object under a revenue key. The collector lifts it out and normalizes it.

pulse('purchase', {
  revenue: { amount: 29, currency: 'USD' },
  plan: 'pro'
});

See Revenue tracking for currency handling and how it merges with Stripe.

Pageviews are automatically deduped against the last URL sent, so a router that both calls pushState and emits its own navigation event won't double-count a single route change.

Calling pulse() before the script loads#

Because the script is deferred, window.pulse may not exist yet when your page code runs. Define a tiny stub that queues calls; the tracker drains the queue the moment it loads.

<script>
  window.pulse = window.pulse || function () {
    (pulse.q = pulse.q || []).push(arguments);
  };
</script>
<script defer data-key="YOUR_INGEST_KEY" src="https://your-pulse.vercel.app/px.js"></script>

Now any pulse('event', …) call made before the tracker finishes downloading is buffered on pulse.q and replayed in order once it's ready. Put the stub in your document <head>, before any code that might fire an event.

Core API#

Five functions, all importable from @pulse/sdk and re-exported from every framework entry point.

init(config)

init(config: PulseConfig): void

Configure Pulse and — unless you opt out — start automatic pageview tracking. It's safe to call more than once: React Strict Mode and hot reload both do, and a second call rebinds cleanly rather than doubling every pageview. This is the classic way an SDK silently reports 2× traffic in development, and Pulse is built not to.

import { init } from '@pulse/sdk';

init({
  key: 'YOUR_INGEST_KEY',
  host: 'https://your-pulse.vercel.app',
  autoPageviews: true,     // default
  respectDnt: false,       // default
  trackLocalhost: false,   // default
  exclude: ['/admin*'],    // default: []
});

track(name, props?)

track(name: string, props?: EventProps): void

Record a custom event. Passing the name 'pageview' is a shortcut that routes to pageview() (and gets its dedupe).

import { track } from '@pulse/sdk';

track('signup', { plan: 'pro', referrer: 'newsletter' });
track('feature_used', { name: 'export', count: 3 });
track('cta_click');   // props optional

trackRevenue(name, revenue, props?)

trackRevenue(name: string, revenue: Revenue, props?: EventProps): void

Sugar over track(). These two calls produce exactly the same payload:

trackRevenue('purchase', { amount: 29, currency: 'USD' });
track('purchase', { revenue: { amount: 29, currency: 'USD' } });

pageview(url?)

pageview(url?: string): void

Record a pageview. Defaults to window.location.href. Deduped against the last URL sent, so calling it twice for the same URL is a no-op. Pass an explicit URL when your router knows the destination before the address bar does.

import { pageview } from '@pulse/sdk';

pageview();                       // current URL
pageview('https://app.dev/pricing'); // explicit

teardown()

teardown(): void

Stop automatic tracking, unbind the route listeners, restore the original History methods, and forget the config. The framework adapters call this for you on unmount; you rarely need it directly.

TypeScript types#

All exported from every entry point.

interface PulseConfig {
  key: string;
  host: string;
  autoPageviews?: boolean;   // default true
  respectDnt?: boolean;      // default false
  trackLocalhost?: boolean;  // default false
  exclude?: string[];        // default []
}

interface Revenue {
  amount: number;            // major units — 29 means $29.00
  currency?: string;         // ISO 4217, default 'USD'
}

type EventProps = Record<string, string | number | boolean | Revenue | undefined>;

Event properties must be scalars — string, number, or boolean — plus the special revenue object. Nested objects and arrays are dropped server-side to keep the events table lean.

Concepts

Pageviews & SPA routing#

By default Pulse tracks a pageview on first load and on every client-side navigation. It does this by wrapping the History API and listening for the browser's own navigation events.

SignalFires a pageview?Why
history.pushStateYesThe normal SPA navigation. Patched so the original still runs, then a pageview fires.
popstateYesBack / forward navigation.
hashchangeYesHash routers change the URL without touching History.
history.replaceStateNoRouters use it for query-param updates and scroll restoration — not real navigations.

Dedupe

Every pageview is checked against the last URL sent. If a router both calls pushState and fires its own event for one route change, only one pageview is recorded.

Prerender awareness

Chrome prerenders pages a user may never actually look at. The script defers the initial pageview until the page becomes visible, so a prerendered-but-unseen page isn't counted — exactly the vanity inflation the public stats page is designed to avoid.

Hash routes become distinct pages

The History API never sees the URL fragment, so the collector treats a leading #/ as part of the path. example.com/#/settings is recorded as /#/settings, meaning hash-router views show up as separate pages instead of everything collapsing onto /.

Some frameworks don't route through pushState. Next.js App Router, vue-router and SvelteKit can navigate without it, so the History patch may miss pages. For those, use the framework adapter (which drives pageviews from the router) or call pageview() yourself. See Frameworks.

Custom events#

A custom event is any named signal that isn't a pageview — a signup, a click, a feature toggle, a funnel step. Give it a name and, optionally, a flat bag of scalar properties.

import { track } from '@pulse/sdk';

// Simple named event
track('newsletter_subscribe');

// With properties — strings, numbers, booleans
track('plan_selected', { plan: 'pro', annual: true, seats: 5 });

// The script-tag equivalent
// pulse('plan_selected', { plan: 'pro', annual: true, seats: 5 });

Naming

  • Names are trimmed and truncated to 64 characters server-side.
  • An empty name is rejected (400).
  • The name 'pageview' is reserved — it routes to pageview tracking.
  • Prefer stable, lowercase, snake_case names (cta_click) so they group cleanly in the dashboard's funnels and event breakdowns.

Properties

  • Up to 24 keys; extra keys are dropped.
  • String values are truncated to 500 characters.
  • Only string, number (finite), and boolean are kept. Nested objects/arrays are ignored — except the reserved revenue object.

Revenue tracking#

Revenue is a first-class citizen in Pulse. Anything you can't wire to Stripe — Gumroad, Lemon Squeezy, Paddle, a manual invoice, an ad payout — you can report through the SDK, and it lands in the same pipeline as your Stripe webhooks. Every money query then reads one table.

Two equivalent forms

import { track, trackRevenue } from '@pulse/sdk';

// Dedicated helper (clearest)
trackRevenue('purchase', { amount: 29, currency: 'USD' }, { plan: 'pro' });

// Or inline on any event
track('purchase', { revenue: { amount: 29, currency: 'USD' }, plan: 'pro' });
// Script tag — revenue rides inside props
pulse('purchase', { revenue: { amount: 29, currency: 'USD' } });

Amounts are in major units

Pass 29 for $29.00 — not 2900. The collector converts to integer minor units in the currency you charged, so nothing is ever stored as a float. Zero-decimal currencies like JPY and KRW, and three-decimal ones like KWD, are handled correctly server-side.

FieldTypeNotes
amountnumberMajor units. Must be finite and ≥ 0 — a NaN or negative amount is rejected outright rather than coerced to zero, because a corrupted public revenue figure is the one number people actually check.
currencystringISO 4217, case-insensitive. Defaults to USD if omitted or malformed.

Where it shows up

SDK revenue is stored as a normalized record with source: 'sdk' and kind: 'one_time', alongside Stripe rows. It appears on the dashboard's revenue view and — if you've enabled revenue on the public page — in the public totals. If you've set PULSE_FX_RATES on your deployment, mixed currencies are normalized into one display total; anything unconverted is flagged in the UI rather than silently misreported.

A revenue event is also a regular event — the purchase is recorded even if the money side fails. If the revenue row can't be written, the pageview/event is still durable and the failure is logged server-side, never surfaced to the fire-and-forget client.

Framework adapters

Overview#

Each adapter wires init() into a framework's lifecycle and, crucially, drives pageviews from the framework's own router — which is more reliable than the core History patch for frameworks that navigate without pushState. The core stays framework-free; adapters are only pulled in when you import their entry point.

React @pulse/sdk/react#

Two hooks, plus re-exports of the whole core API.

usePulse(config)

Initializes Pulse for the lifetime of the component and tears it down on unmount. Keyed on the config values, so an inline config literal doesn't cause a rebind on every render.

import { usePulse, track } from '@pulse/sdk/react';

function App() {
  usePulse({ key: 'YOUR_KEY', host: 'https://your-pulse.vercel.app' });

  return <button onClick={() => track('cta_click')}>Start</button>;
}

Mount it once, high in your tree. For routers that use pushState on every navigation (React Router), the default autoPageviews is enough.

usePulsePageviews(path)

Fires a pageview whenever path changes. Use it when your router doesn't go through pushState — see the Next.js pattern below. Passing null/undefined is a no-op, so it's safe during the first render before a path resolves.

Next.js App Router#

App Router navigations don't always go through pushState, so turn off the History patch and drive pageviews from the pathname instead.

'use client';
import { usePathname } from 'next/navigation';
import { usePulse, usePulsePageviews } from '@pulse/sdk/react';

export function Analytics() {
  usePulse({
    key: 'YOUR_KEY',
    host: 'https://your-pulse.vercel.app',
    autoPageviews: false,
  });
  usePulsePageviews(usePathname());
  return null;
}

Render <Analytics /> once in your root layout.tsx. Because it's a client component that renders null, it costs nothing visually and initializes tracking on first paint.

Want to also capture query-string changes as distinct pageviews? Combine usePathname() with useSearchParams() and pass a joined string to usePulsePageviews(). Wrap that component in <Suspense>, as useSearchParams() requires.

Vue @pulse/sdk/vue#

A plugin plus an optional router hook. It takes a router-like object rather than importing vue-router, so it works with vue-router 3 and 4 and forces no dependency.

import { createApp } from 'vue';
import { createPulse } from '@pulse/sdk/vue';
import App from './App.vue';
import router from './router';

const app = createApp(App);

app.use(createPulse(
  { key: 'YOUR_KEY', host: 'https://your-pulse.vercel.app' },
  router,
));

app.mount('#app');

Passing the router lets its afterEach hook drive pageviews — more reliable than patching History, since vue-router doesn't always go through pushState. When you pass a router, autoPageviews defaults to false automatically so you don't double-count.

$pulse in templates

The plugin adds a global $pulse property exposing track, trackRevenue and pageview:

<button @click="$pulse.track('cta_click')">Start</button>
<button @click="$pulse.trackRevenue('purchase', { amount: 29 })">Buy</button>

Svelte / SvelteKit @pulse/sdk/svelte#

SvelteKit navigates without pushState in some cases, so the binding takes the page store's URL rather than relying on the History patch. It's SSR-safe: on the server it returns a no-op, so there's nothing to guard.

<!-- src/routes/+layout.svelte -->
<script>
  import { onDestroy } from 'svelte';
  import { page } from '$app/stores';
  import { pulse } from '@pulse/sdk/svelte';

  const stop = pulse(
    { key: 'YOUR_KEY', host: 'https://your-pulse.vercel.app' },
    page,
  );
  onDestroy(stop);
</script>

pulse(config, page?) returns an unsubscribe function — call it in onDestroy to tear tracking down. Passing the page store makes pageviews follow SvelteKit navigations; the store's initial synchronous emit is deduped so the first load isn't counted twice. When you pass page, autoPageviews defaults to false.

For plain Svelte (no SvelteKit router), call pulse(config) with no store to fall back to the History-based auto tracking.

Privacy & filtering

Opt-out & Do Not Track#

Pulse sets no cookies, writes nothing to localStorage, uses no fingerprinting, and does no cross-site tracking. There are three ways an individual visit can be excluded.

The pulse_ignore flag

Set a single localStorage key in any browser you don't want counted — your own, mainly, or a staging environment. The SDK reads this flag on every send and never writes it.

// Run once in the browser's console, or from your own admin UI
localStorage.pulse_ignore = '1';

// To start counting yourself again
delete localStorage.pulse_ignore;

Do Not Track & Global Privacy Control

Opt in to honouring DNT / GPC with respectDnt: true (or the data-respect-dnt attribute). When on, events from browsers signalling either preference are dropped. The collector also checks the DNT and Sec-GPC request headers, so the preference is respected even if someone posts to the endpoint directly rather than through the tracker.

How unique visitors are counted

No identifier is stored. A visitor is a salted daily-rotating hash computed on the server:

sha256( daily_salt + project_id + ip + user_agent )

Every input except the salt is already in an ordinary HTTP request, and none of them is stored — the IP is used to compute this and look up a country, then discarded. The salt is random per UTC day and destroyed after 48 hours, after which that day's hashes can't be recomputed or reversed by anyone, including the site owner. That's what makes "we can't track you across days" a property of the system rather than a promise.

Excludes, localhost & bots#

Excluding paths

Skip routes with exclude (SDK) or data-exclude (script). Exact match, or prefix match with a trailing *.

init({
  key: 'YOUR_KEY',
  host: 'https://your-pulse.vercel.app',
  exclude: ['/admin*', '/preview', '/checkout/success'],
});

Localhost & development

By default Pulse does not track localhost, 127.*, ::1, *.local, or file:// pages, so your dev server never pollutes real numbers. Opt in with trackLocalhost: true or data-local when you specifically want to test the pipeline end to end.

Bot filtering

The tracker skips obvious automation client-side as a cheap optimization — it checks navigator.webdriver and known headless globals (_phantom, __nightmare, callPhantom) and simply doesn't send the request. The real filtering happens on the server against a maintained bot list, at a per-project sensitivity level. Bot events are dropped quietly (202) rather than stored.

Domain allow-list#

Because the ingest key is public, it can't be what authorizes a write. The real defense against forged events is your project's domain allow-list, configured in the dashboard. If set, the collector only accepts events whose URL hostname matches.

  • An entry also covers its subdomains — adding example.com accepts www.example.com and blog.example.com too.
  • A leading www. is normalized away on both sides.
  • If the list is empty, all domains are accepted (convenient for getting started; tighten it before you publish a stats page).

The allow-list is why it's safe to expose data-key in your HTML: an event forged from another domain is rejected before it's ever stored.

Reference

Wire format#

Both the script and the npm package POST a small JSON body to /api/event as text/plain — which keeps it a CORS "simple request" with no preflight, so a pageview costs exactly one round trip. Keys are single letters because this is the hot path.

POST https://your-pulse.vercel.app/api/event
Content-Type: text/plain

{
  "k": "YOUR_INGEST_KEY",          // project ingest key
  "n": "pageview",                  // event name
  "u": "https://acme.dev/pricing?utm_source=hn",  // full href
  "r": "https://news.ycombinator.com/",           // referrer, or null
  "w": 1440,                        // viewport width (server buckets it)
  "p": { "plan": "pro",             // custom props (optional)
         "revenue": { "amount": 29, "currency": "USD" } }
}
KeyMeaningNotes
kIngest keyRequired. Identifies the project.
nEvent nameRequired. pageview or a custom name.
uPage hrefFull URL. Only the pathname and UTM keys are kept — the rest of the query string is dropped before the row is written and never stored.
rReferrerdocument.referrer or null. Normalized and grouped server-side.
wViewport widthRaw pixels; bucketed server-side. Not identifying on its own.
pPropertiesOptional. Scalar props plus an optional revenue object.

Transport uses navigator.sendBeacon when available — it survives the page being unloaded — and falls back to fetch with keepalive: true. Either way, the client never reads the response.

You can integrate without any Pulse client at all — from a backend, a webhook, or curl — by posting this exact body to /api/event. A CORS preflight (OPTIONS) is answered for JSON Content-Type if you post from a browser.

What the server does with your event#

The client stays dumb on purpose. Everything below is derived on the edge from data the request already carries, then the raw inputs are discarded.

Derived & stored

  • Device, browser, OS — from the User-Agent
  • Country & region — from edge geo headers
  • Referrer host + channel group
  • UTM source / medium / campaign / term / content
  • Screen-size bucket — from viewport width
  • A salted daily visitor hash

Discarded, never stored

  • The raw IP address (used, then dropped)
  • The full User-Agent string
  • Everything in the query string except UTM keys
  • The URL fragment (except a leading #/ route)

HTTP responses#

The client is fire-and-forget and ignores the response, so the collector stays deliberately quiet: it only distinguishes cases the site owner can act on. A status code never reveals whether a key exists, a domain is allow-listed, or a bot evaded the filter.

StatusMeaningWhen
202AcceptedThe normal success — and most quiet rejections (unknown key, archived project, bot, excluded path, DNT). Indistinguishable from outside on purpose.
400Bad payloadThe one rejection worth surfacing: malformed JSON, missing key, missing/empty name, or an unparseable URL. It means the integration is broken.
429Rate limitedToo many events from one IP. Includes a Retry-After header. The limiter is a spike damper, not a hard quota.
503Not configuredThe deployment is missing its service-role key, or a lookup failed. A server-side misconfiguration to fix.

Guardrails applied server-side so one caller can't bloat the busiest table in the database.

Guides

Recipes#

Track outbound link clicks

document.addEventListener('click', (e) => {
  const a = e.target.closest('a');
  if (a && a.host !== location.host) {
    pulse('outbound', { href: a.href });
  }
});

Track a form submission

import { track } from '@pulse/sdk';

form.addEventListener('submit', () => {
  track('contact_submit', { form: 'homepage' });
});

Track a file download

pulse('download', { file: 'pricing.pdf' });

Report revenue from a webhook you already have

No client needed — POST the wire format from your server when your payment provider notifies you of a sale.

await fetch('https://your-pulse.vercel.app/api/event', {
  method: 'POST',
  headers: { 'Content-Type': 'text/plain' },
  body: JSON.stringify({
    k: process.env.PULSE_KEY,
    n: 'purchase',
    u: 'https://acme.dev/checkout',
    p: { revenue: { amount: 49, currency: 'USD' }, source: 'gumroad' },
  }),
});

Manual pageviews only

Turn off auto-tracking and fire pageviews on your own terms — handy for wizards or modals you want to count as steps.

<script defer data-key="YOUR_KEY" src="…/px.js" data-manual></script>
<script>
  // later, when a step opens:
  pulse('pageview');
</script>

Troubleshooting & FAQ#

My events aren't showing up

  • You're on localhost — dev traffic is skipped unless you set trackLocalhost / data-local.
  • localStorage.pulse_ignore is set in this browser — clear it with delete localStorage.pulse_ignore.
  • Your domain isn't on the project's allow-list, so events are rejected server-side.
  • The data-key / key is wrong, or the host points at the wrong deployment.
  • Check the Network tab for the /api/event request. A 400 means a broken payload; 202 means accepted (even quiet rejections return 202).

My SPA only records the first page

Your framework navigates without pushState. Use the matching framework adapter, or call pageview() on each route change.

I'm getting double pageviews

Usually two initializations, or auto-tracking left on and a manual driver. Pick one: either autoPageviews: true and nothing else, or autoPageviews: false plus the router hook. init() is safe to call repeatedly, but two different drivers both firing will double-count.

Do I need a cookie banner?

No. Consent requirements are triggered by storing or accessing information on a device, and by processing personal data. Pulse does neither — no cookies, no storage identifiers, no personal data retained. (This isn't legal advice, but it's the same basis Plausible and Umami operate on.)

Is the ingest key a secret?

No. It's public by necessity — it ships in your HTML. The domain allow-list is what protects you, not the key's secrecy.

Does the SDK slow down my site?

The script is 928 B gzipped (measured and enforced in CI), loads deferred, and sends fire-and-forget beacons. The npm package adds no network request and tree-shakes to the functions you use.

Can I self-check the payload before shipping?

Yes — open your browser's Network tab, filter to event, and inspect the request body. It's the wire format above, in plain text.
